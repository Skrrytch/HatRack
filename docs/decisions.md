| 2026-11-08 | `workdir` sensor ([auto-detection.md, 1a](auto-detection.md#1a-working-directory-and-branch-workdir)), new ticket in MVP 8, built alongside #4: the repository and branch of the focused terminal or IDE come from the process tree in `/proc` (working directory) and the one line of `.git/HEAD`; IDEs through their own list of recent projects (JetBrains `recentProjects.xml`, VS Code `workspaceStorage`). Claude Code is covered the same way (process `claude`, its working directory). Its session files carry `cwd` and `gitBranch`, but in the same lines as the conversation, so HatRack never opens them. Getting the key into Claude Code's title was judged and dropped as the main path: the title is the `/rename` name, else a topic title from a separate model call, else "Claude Code"; an instruction in `CLAUDE.md` does not reach it, a hook needs the built-in title off and misses later checkouts, the status line never reaches the window title. `/rename` by hand, or `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` plus the prompt snippet, stay as fallbacks without the sensor. IDE plugins were judged too and rejected: the ActivityWatch watcher for JetBrains sends the branch (of the first repository only), but also full paths, commit and remote URL, to a separate ActivityWatch server; WakaTime-style plugins go to a cloud service with an API key; both mean installing and running something extra. Stored are only the folder name of the work tree (`repo`) and the branch; `ignore`/`redact` apps, hats with `observe: false` and folders in `observe.ignore_paths` give nothing. Terminals that run all tabs in one process (Guake, GNOME Terminal, tmux) give a result only when it is unambiguous. No network, no login, no root. Supersedes "no sensor for the working directory or git repository" in the epic; shell and git hooks stay out. |
| 2026-11-08 | Parallel work and the end of a task ([auto-detection.md, 6a](auto-detection.md#6a-parallel-work-and-the-end-of-a-task)), decided by Bert: an entry keeps one hat, one activity and one detail; no stored shares and no side entries. Reports come from the log, never from observations. A task stays open until an absence, a boundary the user set, a meeting, another hat, or 15 minutes unseen (memory) end it. Afterwards each clock hour is condensed to one entry per task with its summed time, in the order of first appearance (frame rule at the hour's edges); pieces under 5 minutes go to the hour's main task, also across hats (named in the reason, never across working and non-working hats). Following Bert's proposal, tickets of the same hat and activity worked on in turn (each at least 5 minutes and two pieces of 2 minutes in the hour) become **one parallel entry** with the keys as its detail (`ACME-101, ACME-117`, sorted), because only the worker knows the split; different activities or hats are split by their sums. "Parallel" is not stored: an entry is parallel when its detail names two or more keys. The review shows the observed shares and offers "Split". Proposals are compared with the log by sums per window, not by positions, so an accepted proposal never comes back. Live: another hat after 10 of the last 15 active minutes, a new detail only after the old key was unseen for the memory; #9 moves behind the core of #4 into MVP 9. New ticket: day report by phases, from the log. Commit, push, ticket status and calendar are no signals (no git hooks, nothing fetched, no logins). |
