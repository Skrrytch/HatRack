# Decisions

## Made

| Date | Decision |
|---|---|
| 2026-11-07 | Day view band "Observed" and MCP scope `observe` (#7): blocks are per app, with the top three titles only in the tooltip; an app keeps the colour of its name's hash unless a busier app of the day has it (then the next free one), so apps of one day never share a colour; absences are drawn over the windows and subtracted from the app totals; the booked and the observed band share one time axis (widened to cover the observations); clicking a block prefills the add form and writes nothing. The scope `observe` is chosen when a token is created, never added later; existing tokens stay `read`. |
| 2026-11-07 | Absence (#2): the default is booked at once and the question only amends it (nothing blocks; overnight locks stop the clock without an answer). Answers use plain backdated `off`/`switch` events instead of corrections, because devices may not send corrections. A computer stops the clock only if no other computer is in use (`GET /api/presence`); unknown presence blocks the stop, an unreachable server does not. A suspend goes through the same check. Settings in `observe.idle`, edited in the tab Erkennung → Abwesenheit. |
| 2026-11-07 | Detection settings get their own setup page **Erkennung** with tabs (Sensoren: one table sensors × devices, also for devices that never connected; Datenschutz: lists and retention) instead of blocks on the Devices page, which keeps one line per device. Later tickets add a tab each (Abwesenheit #2, Rückfragen #3, Regeln #8); rules themselves stay on the hat's page. Privacy lists and retention apply to all devices, switches are per device (`observe.devices`); sensors are their own type next to modules (`internal/sensors`). |
| 2026-11-07 | Automatic detection, the open questions: an `auto` rule may also start a hat when none is worn (most automation by default; a per-rule `start: ask` can follow). Observations are kept 28 days by default. The GNOME Shell extension is embedded and installed by `hat setup`. Work on the epic is split by model per ticket (Opus 5.5 for design notes, core, concurrency, privacy and the review per MVP; Sonnet 5.5 as default implementer; Haiku 5.5 for mechanical work with a check), see [auto-detection.md](auto-detection.md#model-plan). |
| 2026-11-07 | [Epic: automatic detection](auto-detection.md), MVP 7 to 11, GitHub #14 with the stories #1 to #13. Observations (window, idle, microphone/camera, matched notifications) are stored apart from the event log, with a retention period, and never reach MQTT; the log keeps holding decisions only. Heuristics propose; a proposal enters the log only when accepted, as one `correction` with a `source`. Only rules with `mode: auto` switch by themselves, and their events carry the rule. Rules live in the configuration per hat; classification is in the core, so agent (live, offline) and server (afterwards) agree. Time blocks are for scoring, reading and asking, not for booking: the log keeps one hat at a time, so a block with two topics becomes two entries in their order. Idle detection moves from MVP 3 to MVP 7 and uses `off` and corrections instead of `idle_start`/`idle_end` events. Implementation in Go with `xgb`, D-Bus and `/proc` instead of `xdotool`, `xprintidle`, `zenity` or `rofi`; prompts use the own panel. No keylogging, screenshots, content or calendar logins. |
| 2026-11-04 | Name **HatRack**; command `hat`, tray **HatTray**, server **HatRack Server**. |
| 2026-11-05 | Release artifacts for end users: a `.tar.gz` per architecture (amd64, arm64) with an `install.sh` that installs into `~/.local/bin` without root, a `.deb`, and a container image of the server. All are built from one tag, with checksums. After installing, `hat setup` does the rest, as today. Agent and tray always run natively in the user's desktop session; only the server may run in a container. Not for now: rpm, AUR. Rejected: Flatpak and Snap (the sandbox blocks host gsettings, `gtk-launch`, user services and the tray), AppImage (no gain for a static binary). `scripts/update.sh` stays the developer path. Stated support: Cinnamon on X11; on other desktops the time log, `launch`, notifications and MQTT work, but the look does not change until they get backends. |
| 2026-11-05 | `hat setup` stays as short as it is: it asks only where the server runs (here, or an address and token), no third answer for a container. The container server is the documented alternative (`deploy/compose.yaml`, then `hat setup --server`). Not planned: writing compose or Quadlet files from setup, moving data between a local and a container server (copy the data directory). Possible later and small: device tokens in the web UI, so no `docker compose exec` is needed. Done with MVP 6: `hat update`, self-restart of agent, server and tray after their binary was replaced, version check between agent and server in the hello. |
| 2026-11-05 | When the user's session ends, the agent takes the hat off as "Stop" does (clock stops, neutral look returns). It acts on a stop signal only if `systemctl --user is-system-running` says `stopping`, so a restart for an update or `hat agent install` leaves the hat on. The event is sent at once, or queued if the server is down. The unit orders the agent after `dbus.socket` so the desktop is still reachable; units installed earlier need `hat agent install` again. Not covered: crash, power loss, lingering sessions. If the look does not come back on a real desktop, add the logind `PrepareForShutdown` signal with a delay lock. |
| 2026-11-05 | The tray menu has no pause or resume; both are in the panel. The tray menu lists Einrichtung, Woche, Tag and Jetzt flat, in that order, above "Über HatRack". The tray does not know the browser's access: the Einrichtung link always shows, and the login page answers when no session exists. Access is per browser session (`auth.go`), not per device token. |
| 2026-11-04 | Client/server split with an optional server; the core is a library so a standalone mode can follow without a rewrite. |
| 2026-11-04 | Modules with per-desktop backends; no dependency on one distribution, display server or UI toolkit. |
| 2026-11-04 | Commits carry no AI attribution (see `CLAUDE.md`). |
| 2026-11-04 | The MVP comes in three stages: [MVP 1](mvp-1.md), [MVP 2](mvp-2.md), [MVP 3 and outlook](mvp-3.md). |
| 2026-11-04 | Configuration (hats, activities, module settings) can be exported and imported as YAML, on the server and locally, so a setup moves with one export and one import. |
| 2026-11-04 | Activities are optional. Per hat: `resume_activity: never \| last \| ask`. Unknown activities are rejected. |
| 2026-11-04 | Hat and activity names ignore case and accept unique prefixes. |
| 2026-11-04 | `hat off` is a pause: the look stays, only the clock stops. `hat off --neutral` restores the neutral look. |
| 2026-11-04 | No `hat menu` for now. HatTray and `hat tray run\|show\|hide\|toggle` first planned for MVP 3, moved to MVP 2 (see below). |
| 2026-11-04 | One state per user: a switch on any device switches all devices, and the log never has overlapping intervals. Rejected: one state per device (overlaps, every report needs a rule which device counts; high effort, little benefit for one user). A per-device "don't follow" flag that only skips applying the look can come later without changing the model (see [MVP 3 and outlook](mvp-3.md)). |
| 2026-11-04 | Licence MIT, as for OTP-Scout. Public repository on GitHub. |
| 2026-11-04 | Go instead of Python: one static binary `hat` for CLI, agent, server and tray, no runtime to install, independent of the distribution. Web UI with `templ` + HTMX, tray with `fyne.io/systray` (StatusNotifierItem over D-Bus, no GTK/Qt), D-Bus with `godbus/dbus`, SQLite with `modernc.org/sqlite`, MCP with the official Go SDK. External modules are executables speaking JSON over stdin/stdout. Rejected: Rust (slower development for a glue-heavy tool), TypeScript (needs a runtime, weak D-Bus and tray support). |
| 2026-11-04 | User interface in English and German. The web UI picks the language from the browser (`Accept-Language`) and can be switched; CLI, tray and notifications follow the locale (`LC_MESSAGES`/`LANG`) and can be overridden with `language: auto \| en \| de`. All texts come from message catalogs from MVP 1 on. |
| 2026-11-04 | The activity is always introduced by `do`: `hat on venom do review` mirrors `hat do review` for the current hat. Longer, but one pattern to remember. |
| 2026-11-04 | State transitions: `do` and `off` without a worn hat are errors that write no event. `hat on` / `hat on X` resumes a paused hat with a `switch` event. A backdated event (`--at`) changes the look only if it is the newest event. See [MVP 1](mvp-1.md). |
| 2026-11-04 | Hats are identified by `key`, activities by name within the hat. Renaming a key or an activity creates a new one; history stays with the old one. |
| 2026-11-04 | MVP 1 needs a server (local on `127.0.0.1` is fine); the agent caches the configuration for outages. Standalone mode stays in MVP 3. |
| 2026-11-04 | MVP 1 deviations from the first plan: the "Now" page uses `html/template` with a meta refresh instead of `templ` + HTMX (one read-only page does not justify a generator and a script; both come with the full web UI in MVP 2); messages come from a small embedded catalog (`internal/i18n`) instead of `go-i18n` (only `%s` placeholders are needed so far); the module is called `hatrack`; Go 1.24 or newer (`omitzero`). |
| 2026-11-04 | The "Now" page needs a device token, given once as `/?token=…` and kept in a cookie, so a server on the network does not show what you are working on. A real login follows with the web UI in MVP 2. |
| 2026-11-04 | Events refer to hats by key and to activities by name, not by an internal id. Keys are stable by design, and the log stays readable on its own. |
| 2026-11-04 | `hat on X` while X is already worn changes nothing (it would otherwise reset the activity); `hat on X do Y` changes the activity. |
| 2026-11-04 | After MVP 1 was built: the command line is the base, but the web UI and the HatTray are the tools used every day. HatTray moves from MVP 3 to MVP 2. MVP 2 is built in slices (read-only web UI, HatTray, Setup forms, corrections, the rest), each usable on its own. |
| 2026-11-04 | Web UI login: one user per server, a password only. It is set with `hat server user set-password` (prompt, or one line from stdin). The password is stored as a bcrypt hash, sessions are random tokens (30 days, only their hash is stored, cookie `HttpOnly` and `SameSite=Strict`), a changed password ends all sessions. Posts also check the `Origin`. Failed logins are slowed down. A device token in `?token=` still gives a read-only view. |
| 2026-11-04 | The web UI stays on `html/template` with a few lines of plain JavaScript (time zone cookie, reload on change) instead of `templ` + HTMX: pages are whole documents, forms work without scripts, and there is no generator and no third-party script to vendor. Times are shown in the browser's time zone (cookie), else the server's (`--timezone`). |
| 2026-11-04 | In the web UI, `resume_activity: ask` counts as `never`: the activity buttons are right next to the hat. |
| 2026-11-04 | HatTray: `hat tray hide` ends the tray process and `show` starts it, because `fyne.io/systray` cannot hide the icon of a running process on Linux. Clicking a hat is `hat on <hat>`, so its `resume_activity` applies; "Hat only" in the submenu starts it without an activity. |
| 2026-11-04 | Icon: a dark rounded square with a frame in the hat's colour and a cream top hat whose band has the hat's colour; grey (`#8a8f98`) while paused or without a hat. Designed by Bert, drawn in code by `internal/icon` for the tray and used as `hatrack.svg` (blue) for the web UI favicon. |
| 2026-11-04 | Panel (quick switcher) instead of a long tray menu: a left click on the tray icon or `hat panel` (keyboard shortcut) opens a small window with all hats and activities; right click gives a slim menu (open, pause/resume, about, quit). Technique: own X11 window in pure Go (no toolkit, no cgo, embedded Go fonts, software drawing), Wayland later as another backend. Icon code moved to `internal/icon`. |
| 2026-11-04 | First-time setup is one interactive command, `hat setup`: it asks where the server runs (here by default, else address and token), installs server and agent as user services, creates this computer's device token itself (no copying for a local server), asks for the web password, offers two starter hats and sets up the tray. It can be run again; flags (`--server`, `--token`, `--yes`, `--no-services`, `--no-tray`) make it scriptable. A setup page in the web UI can later build on the same steps. |
| 2026-11-04 | Module settings are checked per hat together with the defaults they extend: a hat may set only what differs (e.g. the wallpaper fit), and defaults may lack a required value as long as every active hat ends up with one. |
| 2026-11-04 | Renaming an activity in Setup renames it from then on; the time log keeps the old name for past entries, because events store activity names as text. Hats are renamed by their display name only; the key stays and the log follows. |
| 2026-11-04 | The server reports an event revision (`event_rev`, growing with every stored event) with each state and in the answer to `POST /api/events`. An agent ignores states older than its last sent events, so a late state message cannot undo a switch. |
| 2026-11-04 | Corrections in the Day view are planned on the timeline as it counts now and stored as exactly one `correction` event (superseded ids plus replacement events; identical events are kept, so a correction holds only what changed). Changing an entry's start or making it shorter moves the neighbour's boundary; making it longer covers what was there, and what ran at the new end goes on. Deleting leaves a gap. An entry without an end means "since then, and it goes on". Undo is again a correction. Corrections by an AI (MCP) will start as `proposed` and count only once confirmed. |
| 2026-11-04 | Working hours are a setting of the defaults (`defaults.work_hours: {start, end, days}`, default Monday to Friday 08:00–18:00). The Day view shows them and widens to whole hours only for entries outside; time outside is hatched, a day off is hatched as a whole. Archived hats and activities stay listed, but folded away. |
| 2026-11-04 | Pick lists in Setup come from the devices: an agent lists installed GTK and Cinnamon themes and the wallpapers in the pictures folder and `/usr/share/backgrounds` (two levels, at most 150) with 160×100 JPEG previews, cached in `~/.cache/hatrack/thumbs`. It sends them in a second hello after connecting, so switching never waits. Theme fields offer suggestions but stay free text; the wallpaper is a gallery that fills in the path. The server only shows previews that are plain JPEG `data:` URIs. |
| 2026-11-04 | Web UI design (chosen by Bert from three rounds of mock-ups): navigation as a pill bar in the middle of the header; on Now a large tilted hat silhouette in the hat's colour, "since" above the large duration and "today" below it on the right; hats as cloakroom tickets (colour bar, perforation, today's total as a stamp); the day as a band with labels, a "now" mark and the working hours, at the bottom of Now and at the top of Day. Light and dark follow the system; the styles live in `static/hatrack.css`. |
| 2026-11-04 | Module `launch` opens what a hat needs when it is put on (`apps`: `.desktop` ids via `gtk-launch`; `open`: addresses, folders, files via `xdg-open`), started detached. It never closes anything when a hat comes off, because closing windows on the user's behalf can lose work. It runs on a look change, so pausing and resuming the same hat does not open things twice. Lists of strings in module schemas appear in Setup as one entry per line, with a pick list where the device reports choices (installed programs). |
| 2026-11-04 | The Devices page shows a new device's token once, in the answer to the form, never in an address; removing a device revokes its token, its entries stay. Archived hats that no event or correction refers to can be deleted for good. |
| 2026-11-04 | MCP starts read-only: its main purpose is reading the time log (totals by hat, activity, day, week) and the configuration, for Claude Code over HTTP at `/mcp`. MCP tokens are separate from device tokens, managed in Setup, scope `read` only for now. Switching, proposals, notes and a stdio bridge come later, if at all. |
| 2026-11-04 | Totals are rounded to minutes by largest remainder (`core.Apportion`, `core.RoundTotals`): activities add up to their hat, hats to the total, days to the week, CSV rows to the week. Rounding each part on its own let many short entries drift from the total. Web UI, CSV and MCP use the same functions, so their numbers agree. |
| 2026-11-04 | [MVP 4](mvp-4.md): detail suggestions reach back eight weeks (`core.RecentWindow`) and are sent per hat with the activity they were used with. The panel gets a detail field at the bottom of every hat card; its suggestion list floats over the panel, so the card stays small. The worn hat keeps two detail chips. |
| 2026-11-04 | Six hat colours instead of the old fallback palette: purple, orange, aqua, brown, pink, mint (`core.HatColors`), chosen so every pair is easy to tell apart (CIELAB distance at least 33). Teal was dropped (too close to aqua), brown darkened. Each colour has two built-in wallpapers, abstract gradients generated for HatRack with Gemini, under the project's MIT licence. |
| 2026-11-04 | Built-in wallpapers are embedded in the binary (about 4 MB) instead of installed by a script: one file to copy, nothing to forget. A device writes them to `~/.local/share/hatrack/wallpapers/` when it lists or applies one. The configuration stores `hatrack:wp01-purple`, not a path, so one configuration fits devices with different home folders. |
| 2026-11-04 | [MVP 5](mvp-5.md): the `mqtt` module runs on the server (`runs_in: core`; the server hands it the defaults' settings and every new state, agents skip it). It only publishes, retained, with a last will for availability; it never subscribes. Optional Home Assistant discovery with the entities `hat`, `activity`, `working`, `since`; details are never sent. Client library `eclipse/paho.mqtt.golang` (MQTT 3.1.1, built-in reconnect) instead of the planned `paho.golang` (MQTT 5 only); tests use an embedded `mochi-mqtt` broker. |
| 2026-11-04 | Security after the review: a device token may record events but change the configuration only with the right "may change the configuration" (Setup → Devices, `hat server device add --config`; the device `hat setup` creates for a local server gets it). The configuration decides what every agent runs locally (scripts, programs), so a leaked token must not be enough. Devices never send corrections; those come from the web UI. MCP `get_config` masks secrets typed in plain text (`****`), `${env:NAME}` stays visible. The server expands only `${env:HATRACK_…}` for its core modules; agents keep expanding every variable for their own modules. Login attempts are checked one at a time. The read-only view by `?token=` (device token in the address, see the MVP 1 entry above) is removed: a token in an address ends up in histories and screenshots, and the password login makes the view unnecessary. Old links lose the token and lead to the login. |
| 2026-11-04 | Correct time log after the review: an activity event carries its hat and never lands in another one (it puts its hat on, as a switch would). Without `--at`, an event is never older than the newest event the state knows, so a device with a slow clock still switches. `do` and `detail` cannot be backdated before the running entry began (use a correction). An event the server refuses (4xx) is set aside instead of blocking the queue; `hat status` counts them. An end before the start in the Day view means "over midnight" only for entries up to 12 hours. Entries shorter than a minute hand their time to the entry that directly follows (`core.Settle`), dropped if a pause follows; lists, totals, CSV, MCP and `hat log` agree. A hat can be "no working time" (`work_time: false`, e.g. Private): recorded, but left out of the sums, "today", MCP `work_minutes`/today and MQTT `working`. |
| 2026-11-04 | Robustness after the review: hook output (`exec`, external modules) goes to temporary files instead of pipes, so a script that starts a program in the background (`firefox &`) no longer holds the agent until the program ends. MQTT compares its settings by value (no reconnect on every Setup save), sends without holding up switches, always sends the newest state last, and uses a client ID with a random suffix. `hat setup` restarts the agent service, `hat agent login` restarts it if it runs. The neutral look is taken anew whenever no hat look is applied, so a wallpaper the user picked by hand comes back after a hat. A desktop backend that is not found (e.g. at login, before the session) is looked for again after 30 seconds. |
| 2026-11-04 | Usability after the review: the panel pastes with Ctrl+V (clipboard), types AltGr characters and keypad digits, deletes a word with Ctrl+Backspace, ignores other shortcuts, and its suggestion list is wider. The Now page's detail field suggests the hat's details of the last weeks. A gap in the Day view is prefilled with the entry before it. Setup shows values as words (built-in wallpapers as "Purple 2", yes/no, translated options) and no longer marks fields as required; the defaults page has its own heading. The command line speaks the user's language in its help, names unknown commands, accepts `hat log heute/gestern/woche/vorwoche` and `hat on do <activity>`, and offers tab completion (`hat completion`). The CSV in German uses `;`, German headings and a BOM; text that looks like a formula is quoted. An import that only changes a hat's module settings is no longer dropped. |
| 2026-11-04 | Performance and polish after the review: the server keeps the effective log in memory and loads it again only when the event revision changes. The week view lays out every day on one time axis (the widest window of the week, hours below, time outside the working hours hatched) instead of stacking durations; the comparison column is left out when the previous week is empty. Labels in the day band end with an ellipsis and disappear where a segment has no room. The language switch stays on the page shown (with its date) and is visible on phones; on phones the tabs get a row of their own and an activity row stays on one line. Messages speak of work, not of wearing: "You are working on", "Work on X", "No hat active", "Stop" instead of "Take off". "Hat" stays the name of a context, and the state names in the API and MQTT (`wearing`) stay as they are. |
| 2026-11-04 | Activities stay fixed categories; a free, optional **detail** names the work more precisely. The first detail of a running entry applies to all of it; a changed detail starts a new entry. Jira keys in details become links learned from issue URLs (as in Ruumble): only the URL shape counts, nothing is fetched, the oldest link per project wins, Setup can reset a project. |
